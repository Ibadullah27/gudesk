# Assumptions and phase notes

1. **Supabase target:** `GUTECH-LLM`, following the user's project choice. The project URL and publishable key are in ignored local env files; the service-role key is only in `backend/.env`. The database password was not copied into files.
2. **Repository paths:** use `/frontend` and `/backend` as requested; the PDF's illustrative tree names these `/client` and `/server`.
3. **Language:** use JavaScript because the PDF prescribes `.js` files; TypeScript was preferred, not mandatory.
4. **Schema changes:** profile photo/contact fields and notifications requested beyond the PDF schema are deferred to new numbered migrations in their feature phase. Phase 2, 3, and 5 use existing tables and RLS. Phase 4 adds migrations 005-006 for resource indexing and uploader-only Storage deletion.
5. **Phase gates:** the user confirmed Phase 0 database setup and explicitly requested Phases 1-10. The user requested proceeding while earlier Supabase authenticated acceptance checks remained unavailable due to this environment's network failure; this limitation is recorded in the README.
6. **Seed credentials:** SQL seed is local/development-only and uses a shared temporary password; seeded accounts must change it at first login. It was not run against the institution project.
7. **CSV account import:** bulk account import accepts JSON `{ "csv": "..." }` with headers `email,full_name,role,roll_no`; `roll_no` is required for student rows. Imports are row-by-row, up to 100 accounts, and report successes/failures without rolling back successful rows.
8. **Temporary credentials:** account creation/reset generates a unique temporary password and returns it once to the admin UI, which instructs admins to share it securely. Accounts require a password change on first login.
9. **Course scope:** Phase 2 creates/edits courses and assigns an active teacher. Student enrollment/search/import is Phase 3. The course endpoint returns a student's enrolled courses when enrollment rows exist.
10. **Enrollment CSV:** accept one roll number per row or a CSV containing a `roll_no`/`roll number` column. Duplicate roll numbers are collapsed; unknown or inactive student roll numbers are reported as unknown. Removing an enrollment deletes only the enrollment row, preserving submissions and grades.
11. **CLI migration versions:** the user reports migrations 001-004 were executed through SQL Editor. CLI history must be reconciled before a future `supabase db push`; do not rerun the SQL. The user says migration 006 was pasted.
12. **External verification:** backend dependencies are installed and the API is running on port 3001. Local API routes and frontend builds passed. This environment cannot reach Supabase, so Auth, database-backed account/course/enrollment/resource/assignment, and Storage actions remain unverified.
13. **Password recovery delivery:** production email delivery requires Supabase Auth SMTP and an allowed frontend reset URL.
14. **Upload URL expiry:** the installed Supabase Storage client has no configurable expiry argument for signed upload tokens. Signed download URLs are set to 60 seconds; upload links remain path-scoped with overwrite disabled and use the expiry Supabase Storage assigns.
15. **Resource indexing:** migration 005 adds a unique storage path and course/date index for the paginated resource list. Apply it after migrations 001-004.
16. **Storage RLS:** sign upload/download links with the authenticated caller's Supabase client so the existing membership policies are checked. Migration 006 narrows direct resource Storage deletion to files registered to the uploading teacher.
17. **Assignment attachments:** assignments are created first, then an optional attachment is uploaded to the existing private `assignment-files` bucket and attached through a validated update. Downloads return 60-second signed URLs.
18. **Assignment deletion:** deletion is rejected with a confirmation-required 409 when submissions exist. On confirmed delete, assignment/submission rows cascade and known Storage objects are removed; cleanup failures are logged after database deletion.
19. **Assignment attempt files:** students submit a file plus optional text. Resubmission uses a new non-overwriting object; the prior file is removed after the database RPC succeeds.
20. **Quiz attempts:** migration 007 supplies atomic user-identity-checked start/save/submit and question replacement. Timeout is auto-scored from the most recently saved answers when the student submits or the client triggers the timeout request; if the client disconnects, the attempt is finalized on its next submission request.
21. **Marks percentages:** course percentage is obtained points divided by total points for graded assignments and completed quizzes only. Pending and unattempted work is excluded until grading/scoring is final; there are no weighting rules in the specification.
22. **Gradebook export:** CSV exports the currently visible student page and assessment columns, matching the paginated gradebook display.
23. **Announcement scope:** administrators post global announcements; teachers post only to courses they teach; students read. All feed queries use the authenticated Supabase client so the existing RLS policies determine which global and course notices the caller can read.
24. **Chat pagination and live names:** each history request returns up to 50 messages before an optional timestamp; sender names are enriched by the backend because student RLS does not grant peer profile reads. Realtime events trigger a scoped latest-history refresh so inserted messages receive their sender name.
25. **Complaint course scope:** optional complaint course choices come from the caller's course list (enrolled courses for students and taught courses for teachers); RLS remains authoritative if enrollment changes before submit.
26. **Profile contact details:** the user profile includes optional phone and alternate contact email fields; the Supabase sign-in email remains read-only because changing it requires the Auth email-confirmation flow.
27. **Profile photos:** photos are private JPG, PNG, or WebP files up to 5 MiB, stored under the user's own UUID path in the `avatars` bucket. The API returns short-lived signed read URLs and the user may only select and remove their own photo.
28. **Notification timing:** event notifications are created by database triggers for announcements, assignments, published quizzes, grades, complaint updates, course enrollments, and resources. Assignment/quiz deadline notifications are stored with `available_at` set to 24 hours before the deadline; the API filters future notices and the client polls every minute so reminders appear at the scheduled time.
29. **Dashboard measures:** student pending work means assignments without a submission and published quizzes without a submitted attempt; teacher ungraded count is submissions without marks; admin complaint count includes only `open` complaints. Deadline cards show future assignment due dates and quiz close dates within seven days.
30. **Phase 11 database migration:** migration 008 adds profile contact/photo fields, private avatar storage policies, notification schema/RLS/triggers, and Realtime publication membership. It must be executed once before these features can use Supabase.
31. **Workspace routing:** sidebar sections are URL routes under the role prefix rather than in-memory state, so the spec's role routes (`/admin`, `/teacher`, `/student`) stay the dashboards and sub-pages are linkable. Admins see Users and Courses as separate pages.
32. **Toast scope:** toasts announce successful actions; errors stay inline next to the form or list that failed so the context is not lost. Quiz answer autosave messages do not toast.
33. **Expired tokens:** the frontend signs out only when the API returns `401` with code `UNAUTHORIZED` (the auth middleware's code), not on wrong-password `INVALID_CREDENTIALS` responses.
34. **Data fetching:** reads use TanStack Query through `useApiQuery`; writes use `apiFetch` followed by targeted `invalidateQueries` calls rather than `useMutation`, which keeps the existing busy/notice/error handling in each form. Classroom chat keeps local state because it merges Realtime events with cursor history and scroll position.
